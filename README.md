# Базис — сайт + CRM

Фронтенд: **React 19 + Vite + React Router**. Бэкенд: `server.js` (Node без веб-фреймворка) — API заказов, клиентов, каталога и прокси ИИ-чата. База данных — **PostgreSQL** (см. «База данных»).

## Запуск

Дважды кликните **`start-site.bat`**: при первом запуске он установит зависимости и соберёт сайт, затем запустит сервер. Повторные запуски сайт не пересобирают. Если сервер упадёт, он перезапустится сам через 5 секунд.

- Сайт: http://127.0.0.1:8787
- Магазин: http://127.0.0.1:8787/shop
- Сайт «Базис Медиа»: http://media.localhost:8787
- Админка: http://127.0.0.1:8787/admin.html

Окно командной строки не закрывайте — пока оно открыто, сайт работает.
Если Node не установлен системно, используется портативная версия из папки `.tools`.

### Постоянная работа (продакшен)

На Windows-сервере сайт работает как служба — без открытого окна, с запуском при старте компьютера:

| Файл | Что делает |
|------|------------|
| `install-service.bat` | от имени администратора: создаёт задачу планировщика «Bazis Site» (SYSTEM, при старте Windows) и запускает её |
| `update-site.bat` | после обновления кода: `npm install`, сборка обоих сайтов, перезапуск службы |
| `uninstall-service.bat` | от имени администратора: останавливает и удаляет службу |
| `run-server.bat` | сам сервер с автоперезапуском; его вызывают `start-site.bat` и служба |

Журнал сервера — в папке `logs/`: файл на каждый день (`server-ГГГГ-ММ-ДД.log`, при размере больше 20 МБ — следующая часть `.2.log`), старше 14 дней удаляются. Настройки в `.env`: `LOG_DIR`, `LOG_KEEP_DAYS`, `LOG_MAX_MB`, `LOG_TO_FILE=0` (только консоль). У каждого ответа есть заголовок `X-Request-Id`, а в ответах с ошибкой — поле `requestId`: по нему ошибка находится в журнале.

Служба дополнительно пишет вывод сервера и сообщения о перезапусках в `server-run.log` (больше 10 МБ — переносится в `server-run.old.log`). Если сервер падает, `run-server.bat` поднимает его через 5 секунд; если он упал 5 раз за 2 минуты (например, не открывается база), — пауза 5 минут со строкой `server crashed 5 times within 120 s` в журнале, затем новые попытки. Если упал сам скрипт, планировщик перезапускает задачу раз в минуту. Остановка и перезапуск службы (`scripts\windows-service.ps1 stop|restart`) сначала просят сервер завершиться штатно (файл `server.stop`) и ждут до 60 с; только потом node завершается принудительно — с записью в `server-run.log`. Состояние: `powershell -ExecutionPolicy Bypass -File scripts\windows-service.ps1 status`.

### Docker или без Docker: только один режим

База данных одна в обоих режимах — PostgreSQL в Docker (сервис `postgres` в `docker-compose.yml`, том `project_bazis-pg`): сайт в Docker подключается к ней внутри Docker, сайт без Docker — по `DATABASE_URL` из `.env` (`127.0.0.1:5432`). Поэтому и для запуска без Docker нужен работающий Docker Desktop (включите в нём «Start when you sign in») либо свой PostgreSQL (см. «База данных»).

Файлы сайта — выпущенные PDF, печать и подпись, ежедневные копии базы (`data/`) и загруженные картинки — живут либо в папке проекта (запуск без Docker), либо в томах Docker `project_bazis-data` и `project_bazis-uploads`. Режим переключается только скриптами — они останавливают сайт, переносят файлы, сверяют их контрольные суммы и помечают прежнюю копию файлом `DATA-MOVED.txt`:

| Файл | Что делает |
|------|------------|
| `switch-to-docker.bat` | папка `data/` → Docker, включает автозапуск Docker (`install-docker-autostart.bat`) |
| `switch-to-windows.bat` | Docker → папка `data/` (прежняя папка сохраняется как `data-old-<дата>`), выключает автозапуск сайта в Docker; база остаётся работать в Docker |

Если `DATABASE_URL` в `.env` указывает не на базу из Docker, скрипты не переключают режим (иначе заказы остались бы в другой базе) и подсказывают, как перенести базу вручную.

На помеченной копии сервер не запускается (код выхода 5) — ни `start-site.bat`/служба на старой папке `data/`, ни контейнер на старом томе, поэтому файлы не разойдутся по двум местам. `start-site.bat` и `update-site.bat` сами выбирают режим: при `data\DATA-MOVED.txt` запускают и обновляют сайт в Docker. Текущий режим: `powershell -ExecutionPolicy Bypass -File scripts\switch-data.ps1 status`.

Здоровье сервера: `GET /api/health` (без пароля, не чаще 60 раз в минуту с адреса) — `200 {"ok":true,"db":"ok",…}`, если база отвечает, иначе `503`. По нему работает `HEALTHCHECK` контейнера. Docker сам `unhealthy`-контейнер не перезапускает, поэтому это делает задача «Bazis Docker Watchdog» (раз в 5 минут): два раза подряд `unhealthy` — `docker restart`, строка в `logs\docker-autostart.log` и оповещение в Telegram через `node notify/cli.js "текст"` (тот же модуль и те же переменные `.env`, что у сервера).

Проверка образа целиком (заказ, заявка, PDF, перезапуск сайта и базы, сохранность данных, пароль админки) — во временных контейнерах (сайт на порту 8799 и свой PostgreSQL в отдельной сети и томах), рабочие данные не затрагиваются: `powershell -ExecutionPolicy Bypass -File scripts\docker-e2e.ps1`.

На Linux — systemd: пример в `deploy/bazis.service` (`Restart=always`). Сборку там делайте при обновлении: `npm ci && npm run build`, затем `sudo systemctl restart bazis`.

## Два сайта: «Базис» и «Базис Медиа»

Код, сервер, база и админка общие; при сборке получаются два сайта с разными разделами каталога:

- **Базис** (`dist/`) — «Управление бизнесом» и «Инфраструктура», с админкой;
- **Базис Медиа** (`dist-media/`) — «Инфраструктура» и «Визуал и медиа», своя главная с портфолио и яркая тема (`src/styles/media.css`), без админки.

Настройки — `shared/sites.json`: разделы каталога, домены (`hosts`), адрес сайта (`url`), порт для разработки, папка сборки. Сервер выбирает сайт по домену запроса (заголовок `Host`); неизвестный домен получает сайт «Базис». Локально медиа-сайт открывается по `http://media.localhost:8787` (браузеры направляют `*.localhost` на ваш компьютер).

Медиасайт по умолчанию **выключен**: включается строкой `MEDIA_SITE_ENABLED=true` в `.env` (только `true` или `false`, иное — ошибка настроек, код 4). Выключенный медиасайт отвечает 404 на всех своих доменах, не попадает в конфиги прокси (`npm run deploy:config`), ссылок на него в сборке нет, стоковое портфолио в `npm run check:prod` не проверяется. После изменения — пересборка (`update-site.bat`).

Перед публикацией укажите домен — иначе ссылки между сайтами будут вести на `localhost`, а на боевом домене медиа-сайт не откроется. Достаточно одной строки в `.env`:

```
SITE_DOMAIN=bazis.kz
```

«Базис» откроется на `bazis.kz` и `www.bazis.kz`, «Базис Медиа» — на `media.bazis.kz` (поддомен — `subdomain` в `shared/sites.json`). Если у медиа-сайта отдельный домен, задайте его явно: `MEDIA_SITE_URL=https://bazis-media.kz` (так же `SITE_URL` для основного; `url` в `shared/sites.json` работает как раньше). Явный адрес важнее `SITE_DOMAIN`. Логика общая для сервера, сборки и конфигов прокси — `config/sites.js`.

Адрес попадает в сборку (canonical, hreflang, ссылки между сайтами), поэтому после изменения запустите `update-site.bat`. Сервер помнит, для какого адреса собран сайт (`dist/.build-info.json`), и при расхождении предупреждает при запуске. Неверное значение (`SITE_DOMAIN=bazis.kz:8080`, `localhost` и т.п.) не даст запустить ни сервер, ни сборку — причина будет в окне или в журнале.

Тексты медиа-сайта, отличающиеся от основного, лежат в `src/locales/sites/media.ru.json` и `media.kk.json`: туда кладутся только те ключи, которые нужно заменить, остальное берётся из общих словарей. Работы в портфолио — `src/content/portfolio.js` (сейчас там примеры со стоковыми фото, замените на свои).

Каждый заказ и заявка помечаются сайтом, с которого пришли (`site`): в админке на вкладке «Заказы» это видно по метке «Базис» / «Базис Медиа». ИИ-консультант тоже знает, на каком сайте его спрашивают, и по чужим разделам отправляет на соседний сайт.

## Как работает заказ

1. Клиент собирает корзину и указывает имя и телефон.
2. Нажимает **Оформить в WhatsApp** (или Telegram).
3. Сайт отправляет заказ на сервер (`POST /api/orders`) и только после успешного сохранения открывает мессенджер с текстом заказа и очищает корзину. Если сохранить не удалось, покупатель видит ошибку, корзина остаётся.
4. Telegram не умеет подставлять текст в чат с человеком, поэтому текст заказа копируется в буфер обмена. Если браузер не дал скопировать, в корзине появляется текст заказа с кнопками «Скопировать» и «Открыть Telegram» — набирать заказ вручную не нужно.

Защита от спама (форма заказа и заявки публичные, капчи нет — `antispam/order-guard.js`):

- перед отправкой браузер берёт одноразовый подписанный токен (`GET /api/orders/challenge`) и в фоне, пока посетитель заполняет форму, решает небольшую задачу (SHA-256 с N нулевыми битами — доли секунды). Без токена, с чужим, повторным или полученным меньше 3 секунд назад токеном заказ не принимается; при всплеске заявок задача усложняется;
- скрытое поле-ловушка: заполнивший его бот получает «успех», но заказ не сохраняется;
- ссылки в имени — 400; тот же заказ с того же телефона в течение 30 минут возвращает уже созданный;
- карточка клиента не создаётся из формы: заказ привязывается к существующей карточке, а новая заводится, когда менеджер переводит заказ «В работу» или «Выполнен». Спам достаточно удалить из «Заказов».

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `ORDER_RATE_LIMIT` / `ORDER_DAILY_LIMIT_PER_IP` | 5 / 20 | заказов с одного адреса за 10 минут / за сутки |
| `ORDER_PHONE_HOURLY_LIMIT` / `ORDER_PHONE_DAILY_LIMIT` | 3 / 10 | заказов на один телефон за час / за сутки |
| `ORDER_GLOBAL_HOURLY_LIMIT` | 100 | заказов со всего сайта за час; сверх — просьба написать в WhatsApp |
| `ORDER_POW_BITS` / `ORDER_POW_SURGE_BITS` / `ORDER_SURGE_PER_HOUR` | 17 / 21 / 30 | сложность задачи обычно / при всплеске и порог всплеска (попыток за час) |
| `ORDER_MIN_FILL_MS` / `ORDER_TOKEN_TTL_MS` | 3000 / 7200000 | минимум от выдачи токена до отправки и срок жизни токена |
| `ORDER_CHALLENGE_LIMIT` | 40 | токенов на адрес за 10 минут |
| `ORDER_DEDUP_MS` | 1800000 | окно склейки повторного заказа |

Запросы с заголовком `X-Admin-Password` проходят без токена и лимитов.

Заявки из ИИ-чата: когда посетитель, написавший хоть что-то в чат, нажимает «Продолжить в WhatsApp» или Telegram, в фоне (`keepalive`, переход не задерживается) уходит `POST /api/orders` с `channel: "chat"`. В CRM это заявка во вкладке «Заявки» с пометкой «ИИ-чат → WhatsApp/Telegram», перепиской, разделом, который смотрел клиент, и телефоном, если он написал его в чате. В текст сообщения WhatsApp подставляется «Номер обращения» — те же 6 символов показаны в карточке заявки, по ним менеджер сопоставляет переписку в мессенджере с заявкой. Одна заявка на разговор; действуют те же токен и лимиты, что у формы. Без телефона карточка клиента не создаётся — впишите номер из мессенджера и переведите заявку «В работу».

Сервер не доверяет данным из браузера:

- название, цена, валюта и сумма позиций берутся из каталога в базе, итог (`totalText`) считается на сервере;
- если товара уже нет, он из раздела «только обсуждение» (`CART_RULES.discussOnlyCategories` в `shared/catalog.json`) или его цена изменилась — ответ `409 catalog_changed`, сайт обновит каталог и попросит проверить корзину;
- количество ограничено `CART_RULES.maxQty`, у позиций из `singleQtyIds` / `singleQtyTitlePattern` — всегда 1;
- дата и `id` заказа задаются сервером (браузер может прислать только случайный UUID `ord_<uuid>` — он защищает от дубля при повторной отправке);
- заказ с сайта не меняет имя и телефон уже существующего клиента CRM, а только дополняет пустые поля;
- запросы на запись принимаются только с `Content-Type: application/json` (защита от отправки форм с чужих сайтов).

## Остатки товаров

Учёт включается для каждого товара отдельно: в админке, в форме товара, флажок **«Учитывать остаток»** и поле **«Остаток, шт.»**. Без флажка позиция продаётся без ограничений (так по умолчанию у всех товаров, в том числе перенесённых из старой базы).

- Заказ списывает товар со склада в той же транзакции, в которой сохраняется. Если чего-то не хватает, заказ не сохраняется целиком, сайт отвечает `409 out_of_stock` и показывает, сколько доступно. Два одновременных заказа на последний экземпляр не пройдут оба.
- Отмена заказа (статус «Отмена») возвращает товар на склад, снятие отмены списывает снова (если товара уже нет, админка сообщит об этом и статус не изменится). При удалении заказа в статусах «Новый» и «В работе» товар возвращается, а в статусах «Готово» и «Отмена» нет.
- На сайте: при остатке 0 — «Нет в наличии», кнопка неактивна; при малом остатке (до 5) — «Осталось: N»; добавить в корзину больше остатка нельзя. Закончившиеся позиции в корзине показываются отдельно и в заказ не входят.
- Если пока вы редактировали товар, остаток изменился из-за продаж или отмен, сохранение не перезапишет его: админка покажет актуальное значение и попросит сохранить снова. Правка других полей (название, цена) остаток не трогает.

## Где смотреть заказы

Откройте `/admin.html` → введите пароль админки → вкладка **Заказы**.

Пароль задаётся на сервере: переменная `ADMIN_PASSWORD` в `.env`, например `ADMIN_PASSWORD=Мой-Пароль-2026`. Пароля по умолчанию нет — сервер не запустится, если `ADMIN_PASSWORD` не задан, пустой, короче 8 символов или из списка самых частых (`bazis`, `admin`, `12345678` и т.п.); причина будет в окне или в `server-run.log`.

Регистр букв учитывается (`Parol` и `parol` — разные пароли). Можно использовать любые буквы, в том числе русские; пробелы в начале и в конце отбрасываются. Проверить настройки, не запуская сайт: `node server.js --check-config`.

Вкладки **Заказы** и **Заявки** загружают записи порциями по 50 (кнопка «Показать ещё»), счётчики по статусам считаются на сервере — админка остаётся быстрой и при десятках тысяч заказов. Вкладки **Клиенты** и **Отчёты** при открытии загружают полный список (только чтение: просмотр списков ничего не меняет в базе).

- **Поиск** над списком: часть имени (без учёта регистра, «ё» = «е»), телефона в любом формате (`+7 701…` и `8 701…` — один номер) или номер обращения из ИИ-чата, плюс период «с / по». Ищет сервер (`GET /api/orders?limit=…&q=…&from=…&to=…`, даты — ISO), счётчики статусов показывают найденное.
- **Итог заказа** учитывает скидки на позиции и на заказ и доставку (вкладка «Документы» в карточке): после каждой правки сервер пересчитывает `totalText` той же функцией, что и счета (`documents/money.js`). В карточке видна разбивка: сумма позиций, скидки, доставка, итог; в ответах API она в поле `totals`.
- Карточка клиента заводится, когда заказ переводят «В работу» или «Готово». Удаление карточки отвязывает от неё заказы — они остаются в CRM. `PATCH /api/orders/:id` с несуществующим `clientId` — `400 client_not_found`.
- Ошибки и подтверждения в админке — уведомления в углу экрана и окно подтверждения (`src/admin/dialogs.jsx`).

Разовые правки данных при запуске (отметки — в настройке `migrations`): привязка старых заказов к карточкам клиентов, очистка ссылок на удалённые карточки, пересчёт итогов у заказов со скидками. Если при запуске из старых JSON-файлов добавлены заказы, правки выполняются снова.

## База данных

**PostgreSQL 16 или новее** (в Docker — `postgres:17-alpine`). Таблицы: `products`, `orders`, `order_items`, `clients`, а для PDF — `settings`, `documents`, `doc_counters`, `document_sends`; версия схемы — в `schema_meta`. Сервер создаёт таблицы сам при первом запуске на пустой базе.

Адрес базы — переменная `DATABASE_URL` (обязательна: без неё или с неверным адресом сервер не запустится, код 4):

```
POSTGRES_PASSWORD=<латинские буквы и цифры, от 16 символов>
DATABASE_URL=postgres://bazis:<тот же пароль>@127.0.0.1:5432/bazis
```

- **В Docker** (`docker compose up -d`) база поднимается сама: сервис `postgres` с паролем `POSTGRES_PASSWORD` из `.env`, данные — в томе `project_bazis-pg`. Сайт ждёт, пока база будет готова, и подключается к ней внутри Docker (`DATABASE_URL` для контейнера задан в `docker-compose.yml` и важнее `.env`). Порт базы опубликован только на `127.0.0.1` (`POSTGRES_HOST_PORT`, по умолчанию 5432) — для сайта без Docker и для `npm run db:*`.
- **Без Docker** сайт подключается по `DATABASE_URL` из `.env` — к базе из Docker (адрес выше) или к своему PostgreSQL: создайте пользователя и базу (`CREATE USER bazis PASSWORD '…'; CREATE DATABASE bazis OWNER bazis;`) и укажите их в `DATABASE_URL`.
- Если база при запуске недоступна, сервер ждёт её до минуты, затем завершается (служба перезапустит его). Если связь пропала во время работы, запросы получают `503 db_unavailable` (сайт повторит позже), в Telegram уходит оповещение, а `GET /api/health` отвечает `503`; когда база вернётся, сервер продолжит работу без перезапуска.
- `DATABASE_URL=pglite:<папка>` — встроенный PostgreSQL в WebAssembly (PGlite, ставится только для разработки) для тестов и опытов без сервера; `npm run check:prod` предупредит, что для работы сайта он не подходит.
- `npm test` не требует PostgreSQL: тесты идут на PGlite. Прогнать тесты хранилища на настоящем сервере: `BAZIS_TEST_DATABASE_URL=postgres://… node --test --test-concurrency=1 db/test/store.test.js documents/test/documents.test.js test/backup-snapshot.test.js` — **указанная база будет стёрта**, только отдельная тестовая; файлы идут по очереди, потому что делят одну базу.

Как устроено:

- Заказы, клиенты и каталог хранятся только на сервере. В браузере покупателя и админа заказы и контакты не хранятся (старые локальные копии удаляются при открытии сайта).
- Каталог: публичный `GET /api/products`; создание, правка и удаление — только с паролем админки.
- Код работы с базой: `db/store.js` (подключение — `db/connection.js`, схема — `db/schema.js`). Связанные изменения (заказ + карточка клиента + списание остатка) записываются одной транзакцией: применяются либо целиком, либо никак. Пишущие транзакции выполняются по очереди, поэтому одновременные заказы на последний экземпляр, выпуск двух счетов по двойному нажатию и повтор номера документа исключены.
- Загруженные фото товаров: `images/uploads/`. Картинка по ссылке (только `https://`) скачивается сервером и тоже хранится там: сайт не зависит от чужого хостинга. Ссылки на локальную и внутреннюю сеть, не картинки (нужен JPG, PNG, WebP, GIF) и файлы больше 1,5 МБ отклоняются (`security/remote-image.js`). Товары, у которых картинка осталась внешней ссылкой, после запуска переносятся в `images/uploads/` в фоне; без интернета ссылка остаётся до следующего запуска.
- Обновления структуры базы применяются при запуске автоматически; перед этим сервер сохраняет копию `data/backups/bazis-before-v<версия>-<время>.json.gz`.

Переход со старой базы SQLite (`data/bazis.db`). При первом запуске на пустом PostgreSQL сервер сам переносит из неё всё — товары, клиентов, заказы, остатки и резервы, реквизиты, выпущенные документы и нумерацию — в одной транзакции и сверяет число записей. Если что-то не перенеслось, PostgreSQL остаётся пустым, а файл — на месте: причина будет в журнале, после исправления просто запустите снова. После переноса файл (с `-wal`/`-shm`) перемещается в `data/legacy-sqlite/<время>/` — не удаляется. Если файл SQLite появился рядом с уже заполненной базой, он не переносится, а откладывается туда же с предупреждением в журнале. Для сайта в Docker достаточно обновиться (`update-site.bat`): копия данных перед обновлением снимется со старой базы, а новая версия при запуске перенесёт её в PostgreSQL. Переход со старых JSON-файлов (`data/orders.json`, `data/products.json`) работает как раньше: на пустой базе без SQLite они переносятся при первом запуске и откладываются в `data/legacy-json/<дата>/`; появившиеся позже новые заказы и клиенты из них добавляются при следующем запуске.

Копии базы:

- Ежедневные: `data/backups/bazis-ГГГГ-ММ-ДД.json.gz` — одна в день (делается при запуске, а у непрерывно работающего сервера — с наступлением нового дня), хранятся последние 14. Это полный согласованный снимок всех таблиц (сжатый JSON), сделанный без остановки сайта; формат — `db/dump.js`.
- Вручную: `npm run db:dump` — копия в `data/backups/bazis-manual-<время>.json.gz` (или `npm run db:dump -- <файл>`); `npm run db:counts` — сколько записей в каждой таблице. Для сайта в Docker то же внутри контейнера (копия ляжет в том данных): `docker compose exec bazis node scripts/db.js dump` / `counts`.
- Восстановление: остановите сайт и выполните `npm run db:restore -- <файл копии> --yes`. Все данные в базе заменяются копией в одной транзакции (либо целиком, либо база не тронута), текущие данные перед этим сохраняются в `data/backups/bazis-before-restore-<время>.json.gz`. Для сайта в Docker удобнее `restore-backup.bat` (ниже).
- Копии вне Docker (`scripts/offsite-backup.ps1`). Копии в `data/backups` и сама база лежат в томах Docker и пропадут вместе с ними (`docker compose down -v`, сброс Docker Desktop, поломка диска). Поэтому раз в день база, выпущенные PDF, печать и подпись и загруженные картинки дополнительно копируются в обычную папку Windows:
  - `install-backup.bat` — задача планировщика «Bazis Backup» (каждый день в 03:00; если компьютер был выключен — при первой возможности) и сразу первая копия. По умолчанию копии кладутся в `D:\Bazis-backups` (если второго диска нет — в «Документы»). Свои папки, в том числе синхронизируемую с облаком или внешний диск: `install-backup.bat "D:\Bazis-backups;C:\Users\<имя>\OneDrive\Bazis-backups"`;
  - `backup-now.bat` — копия прямо сейчас; `backup-now.bat status` — когда была последняя копия;
  - `restore-backup.bat` — восстановление из самой свежей копии (или перетащите на него папку нужной копии). Попросит ввести «ДА», текущие данные сначала сохранит в `data-before-restore-<дата>`. Если что-то пойдёт не так, прежние данные вернутся автоматически;
  - `uninstall-backup.bat` — удалить задачу (копии остаются);
  - `update-site.bat` при установленной задаче перед обновлением сайта в Docker делает свежую копию. Если копия не удалась, обновление отменяется.

  Каждая копия — папка `bazis-<дата_время>` с `database.json.gz`, файлами и `manifest.json` (SHA-256 каждого файла и число записей). Копия засчитывается, только если в папке назначения все контрольные суммы совпали. Хранятся последние 30 копий. Если копия не удалась, в папке копий появляется `BACKUP-FAILED.txt` с причиной; журнал — `logs/backup.log`. Копии, сделанные до перехода на PostgreSQL (с `data\bazis.db` внутри), тоже восстанавливаются через `restore-backup.bat`: база из них переносится в PostgreSQL.
- Посмотреть базу вручную можно любым клиентом PostgreSQL (pgAdmin, DBeaver, `psql`) по адресу из `DATABASE_URL`. Править данные при работающем сервере не стоит: сервер держит копию каталога для ИИ-консультанта и увидит правку не сразу.

## Документы PDF

PDF собирает сервер (pdfmake в отдельном потоке, шрифт Inter со всеми казахскими буквами и знаком ₸ лежит в `documents/fonts/`, пересобирается командой `npm run fonts`). Всё доступно только с паролем админки.

- **Реквизиты** — вкладка админки «Реквизиты»: данные ИП, банк, подписант, префиксы номеров, примечание к счёту, картинки печати и подписи (PNG/JPEG до 1 МБ, лучше PNG с прозрачным фоном). Незаполненное печатается прочерком.
- **Реквизиты покупателя** — в карточке клиента («Реквизиты для счетов и актов»): физлицо или юрлицо/ИП, БИН, адрес, e-mail, банк, договор. Без них в документ попадают имя и телефон из заказа.
- **Счёт на оплату и акт выполненных работ (форма Р-1)** — в карточке заказа кнопка «Документы»: там же скидки по позициям, скидка на заказ, доставка и ставка НДС (НДС считается включённым в цены; 0 — «Без НДС»). Заявки с формы и отменённые заказы документов не получают.
  - Номера сквозные по году отдельно для счетов и актов, с 1: `<префикс>2026-0001`. Номер выдаётся в транзакции и не повторяется.
  - Если в заказе позиции в разных валютах — по документу на каждую валюту; скидка на заказ и доставка относятся к выбранной «валюте скидки и доставки».
  - Документ «замораживается» при выдаче номера: повторное скачивание отдаёт тот же PDF, даже если заказ, клиент или реквизиты изменились. Такой документ помечается «Заказ изменён»; кнопка «Перевыпустить» аннулирует его и выдаёт новый номер с текущими данными. Аннулированные документы остаются в списке и скачиваются с отметкой «АННУЛИРОВАН».
  - Даты и год нумерации — по времени Алматы (`DOCUMENTS_TZ` в `.env`, если нужен другой пояс).
- **Каталог** — вкладка «Товары»: отметьте позиции (или ничего — тогда весь каталог), выберите «Цены» / «Остатки» и нажмите «Скачать каталог». У каждого товара есть кнопка «PDF» — отдельная карточка. Внешние картинки скачиваются и сжимаются один раз и дальше берутся из кэша `data/cache/images/`.
- **Заявка** — кнопка «PDF» в карточке заявки.

Файлы: выпущенные PDF кэшируются в `data/documents/<год>/`, печать и подпись — в `data/company/` (старые картинки не удаляются: на них ссылаются уже выпущенные документы). Всё это внутри `data/`, поэтому попадает в ваши резервные копии вместе с базой.

### Отправка PDF

Кнопка «Отправить» у документа и у каталога. Каналы включаются переменными в `.env` (после изменения перезапустите сервер; в консоли при запуске видно, какие каналы включены):

```
# E-mail через SMTP (например, почта домена или Яндекс/Gmail с паролем приложения)
SMTP_HOST=smtp.example.kz
SMTP_PORT=465
SMTP_SECURE=1
SMTP_USER=docs@example.kz
SMTP_PASS=...
SMTP_FROM="ИП Базис <docs@example.kz>"

# Telegram: бот присылает файл в рабочий чат (бот должен быть добавлен в чат)
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
```

Каждая отправка документа (успешная или нет) записывается в базу и видна в списке документов заказа.

## Публикация в интернете: HTTPS через прокси

Сервер слушает только `127.0.0.1` по HTTP — в интернет его выводит обратный прокси с HTTPS. Без HTTPS пароль админки (он уходит в каждом запросе) перехватит любой в той же сети.

Порядок публикации:

1. В `.env`: `SITE_DOMAIN=ваш-домен.kz` (см. «Два сайта» выше).
2. `update-site.bat` — сборка под этот домен.
3. `npm run deploy:config` — готовые конфиги прокси с вашими доменами в `deploy/generated/`:
   - `Caddyfile` — Caddy, проще всего на Windows: сертификаты получает и продлевает сам. Запуск: `caddy run --config deploy/generated/Caddyfile`;
   - `nginx.conf` — nginx + certbot (Let's Encrypt), команда certbot — в начале файла.

   Шаблоны — `deploy/*.template`, домены в них не правьте: после смены домена просто запустите команду снова.
4. DNS: A-записи всех доменов (команда их перечислит) — на IP сервера; открыты порты 80 и 443.
5. `npm run check:prod` — проверка: домен задан, сайт собран под него, прокси включён. Код выхода 0 — готово.

Оба конфига перенаправляют HTTP на HTTPS, включают HSTS и базовые заголовки безопасности и передают серверу `Host`, `X-Forwarded-For`, `X-Forwarded-Proto`.

**Адрес посетителя за прокси.** За прокси все запросы приходят с `127.0.0.1`, поэтому сервер берёт адрес посетителя из последнего значения `X-Forwarded-For` — его ставит прокси (более ранние может подделать посетитель; nginx из шаблона их вообще не передаёт, Caddy отбрасывает сам). Иначе лимит заказов был бы общим на весь сайт, а неверные пароли от кого угодно блокировали бы вход в админку всем. Заголовкам доверяем, только если соединение пришло с этого компьютера: сервер слушает лишь `127.0.0.1`, так что снаружи их не подставить. Поэтому режим включён по умолчанию (`TRUST_PROXY=1` в `.env` — то же самое явно); `TRUST_PROXY=0` выключает его, и тогда при первом запросе через прокси в журнале появится предупреждение. Код — `config/proxy.js`.

Защита пароля админки от HTTP:

- страница входа, открытая не по HTTPS и не с этого компьютера, пароль не отправляет;
- админские запросы через прокси принимаются только по HTTPS (`X-Forwarded-Proto: https`); по HTTP или от прокси, который не сообщил протокол, — 403 `https_required`. С самого сервера (`http://127.0.0.1:8787`) админка работает как раньше.

## ИИ-чат

Ключ OpenAI задаётся только в `.env` (`OPENAI_API_KEY`, опционально `BAZIS_AI_MODEL`, `BAZIS_AI_URL`, `AI_TIMEOUT_MS`). Без ключа чат отвечает по каталогу сайта.

Вся ИИ-логика — в папке `ai/`:

- `ai/features/*.js` — функции ИИ. Каждый файл подключается автоматически и доступен по `POST /api/ai/<name>`. Список: `GET /api/ai`.
- `ai/providers/` — провайдеры моделей (сейчас OpenAI-совместимый). Выбор — `AI_PROVIDER` в `.env`.
- `ai/lib/` — общие помощники (сообщения) и механизмы надёжности (повторы, очередь, выключатель).
- `ai/plugins/` — сквозная логика вокруг каждого вызова: логирование, метрики. Свой плагин подключается через `ai.use()`.
- `ai/test/` — автотесты ядра: `npm test`.
- `ai/lib/attachments.js` — разбор вложений чата («+» в виджете): DOCX, XLSX, PPTX, ODT/ODS, PDF (через `unpdf`), RTF, DOC (приблизительно), текст (UTF-8/UTF-16/cp1251), фото JPG/PNG/WebP/GIF. Им пользуются все фичи ядра.
- `POST /api/ai/_attachments` — разбор файла в текст без вызова модели (работает и без ключа: офлайн-консультант тоже видит содержимое). Один файл за запрос, разбор — в отдельном потоке с лимитом памяти и времени; если сервер отказал, браузер разбирает файл сам.
- `POST /api/chat` — старый адрес чата, работает как `consultant`. Принимает только JSON и уже разобранные вложения (до 8 МБ).
- `GET /api/ai/_health` — состояние ядра и метрики (нужен заголовок `X-Admin-Password`).

Надёжность (всё настраивается в `.env`, значения по умолчанию подходят для одного сервера):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `AI_TIMEOUT_MS` | 45000 | общий бюджет времени на ответ, включая повторы |
| `AI_RETRIES` | 2 | повторы при временных сбоях (429, 5xx, обрыв сети) |
| `AI_FALLBACK_MODELS` | — | резервные модели через запятую, если основная недоступна |
| `AI_MAX_CONCURRENT` / `AI_MAX_QUEUE` | 8 / 50 | одновременных запросов к модели и мест в очереди |
| `AI_BREAKER_THRESHOLD` / `AI_BREAKER_COOLDOWN_MS` | 5 / 30000 | после N неудачных запросов подряд (каждый уже со своими повторами) ИИ отключается на паузу, чат отвечает офлайн |
| `AI_LOG` | 1 | `0` — не писать строку в консоль на каждый запрос |
| `AI_VISION` | 1 | `0` — модель не умеет картинки: они заменяются пометкой, запрос не падает |
| `AI_VISION_MODEL` | — | отдельная модель для запросов с картинками (например, `gpt-4o`) |
| `AI_IMAGE_DETAIL` | auto | `low` — дешевле, `high` — лучше читает мелкий текст на фото и сканах |

Защита от накрутки расходов (публичные ИИ-адреса доступны любому посетителю):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `AI_DAILY_TOKENS` | 3000000 | общий лимит токенов OpenAI в сутки (UTC) на все запросы с сайта; при исчерпании чат отвечает по каталогу. Расход хранится в базе и переживает перезапуск, виден в `GET /api/ai/_health` (`budget`). Админские функции учитываются, но не блокируются. `0` — без лимита |
| `AI_MAX_OUTPUT_TOKENS` | 1200 | потолок длины ответа модели (у консультанта — 900) |
| `AI_DAILY_REQUESTS_PER_IP` | 150 | вопросов ИИ с одного адреса в сутки — один посетитель не выберет общий лимит |
| `AI_ATTACHMENTS_PER_MINUTE` / `AI_ATTACHMENTS_PER_DAY` | 10 / 100 | разборов файлов с одного адреса |
| `AI_ATTACHMENTS_CONCURRENT` / `AI_ATTACHMENTS_QUEUE` / `AI_ATTACHMENTS_TIMEOUT_MS` | 2 / 6 / 30000 | одновременных разборов на сервер, мест в очереди и время на один файл |
| `AI_IMAGE_TOKENS_LOW` / `AI_IMAGE_TOKENS_HIGH` | 3000 / 26000 | оценка картинки для резерва бюджета (фактический расход берётся из ответа OpenAI) |
| `AI_HISTORY_SECRET` | создаётся сам | ключ подписи реплик консультанта; без него генерируется и хранится в базе |

Цены консультант берёт только из каталога в базе сервера — каталог из браузера не принимается. Свои прошлые реплики в истории диалога сервер принимает только с подписью (`sig`), выданной вместе с ответом: сочинить в браузере «консультант обещал скидку» не получится. Вдобавок в лимитах кабинета OpenAI (Settings → Limits) стоит задать месячный бюджет — это последняя страховка.

Зрение: ИИ видит фото из чата, картинки внутри DOCX/PPTX/ODT и страницы PDF-сканов (до 3 страниц). Параллельно с ответом ядро получает краткое описание картинок (`imageNotes`), а чат хранит его в истории, чтобы ИИ помнил фото в следующих репликах. Фича может сделать дополнительный вызов модели через `ctx.complete(messages, opts)`.

Запросы не по теме (`ai/lib/topic.js`): отдельный вызов-классификатор (JSON, temperature 0) оценивает вопрос и каждое вложение — текст, документ или картинку. Если ничего не относится к услугам сайта, консультант возвращает стандартный отказ с названиями файлов и разделами каталога (`offTopic: true`, основная модель при вложениях не вызывается). Если не по теме только часть файлов, они не передаются модели, а перед ответом стоит пометка (`offTopicFiles`). Приветствия и короткие «да/спасибо» код пропускает сам; если классификатор недоступен — запрос обрабатывается как обычно. Без ИИ-ключа то же делает офлайн-консультант по ключевым словам. Если `buildMessages` фичи вернул `null`, ядро не вызывает модель.

Новая функция — один файл в `ai/features/`:

```js
module.exports = {
  name: "faq",                 // URL: /api/ai/faq
  access: "public",            // или "admin" — нужен пароль админки
  temperature: 0.3,
  parseInput(body) { return { question: String(body.question || "") }; },
  buildMessages(input) {
    return [
      { role: "system", content: "Ты отвечаешь на частые вопросы ИП «Базис»." },
      { role: "user", content: input.question },
    ];
  },
};
```
